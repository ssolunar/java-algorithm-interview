### P1. 유효한 팰린드롬

- **난이도** ★ | [문제 링크](https://leetcode.com/problems/valid-palindrome/) | 책 풀이: [P1_1.java](../../src/ch06/P1_1.java) · [P1_2.java](../../src/ch06/P1_2.java) · [P1_3.kt](../../src/ch06/P1_3.kt) | 내 풀이: [P1.java](solutions/P1.java)
- **첫 시도** ⬜ 자력 해결 / ✅ 힌트 후 해결 / ⬜ 책 참고
- **접근**
  - 정규식으로 영숫자만 남기고 소문자로 변환: `s.replaceAll("[^a-zA-Z0-9]", "").toLowerCase()`
  - 앞 절반만 돌면서 `i`번째와 `len - i - 1`번째 문자를 비교, 하나라도 다르면 `false`
- **복잡도** 시간 `O(n)` / 공간 `O(n)` (전처리한 문자열을 새로 만들기 때문)
- **내 풀이 vs 책 풀이**

  | | 내 풀이 | 풀이 1 (P1_1, 투 포인터) | 풀이 2 (P1_2, 뒤집기) |
  | --- | --- | --- | --- |
  | 전처리 | `replaceAll` 정규식 | 없음 (그 자리에서 건너뜀) | `replaceAll` 정규식 |
  | 비교 | 인덱스로 양 끝 비교 | `start`/`end` 포인터 | `StringBuilder.reverse()` 후 `equals` |
  | 추가 공간 | O(n) | **O(1)** | O(n) |

  - 내 풀이는 풀이 2의 전처리와 풀이 1의 비교 방식을 섞은 형태.
  - 풀이 1은 새 문자열을 만들지 않고 원본 위에서 `Character.isLetterOrDigit()`로 건너뛰며 비교해서 가장 빠르다.
    - `isLetterOrDigit()`는 한글 같은 유니코드 문자도 `true`라서 `[A-Za-z0-9]`와 완전히 같지는 않음. 이 문제는 ASCII 입력이라 차이 없음.
  - 풀이 2는 코드가 가장 짧다.
  - `if (s.equals(" ")) return true;`는 불필요했다. 공백만 있는 입력은 전처리 후 `""`가 되고 반복문이 안 돌아서 어차피 `true`.
  - `if (같으면) continue; else return false;` → `if (다르면) return false;` 한 줄이면 충분.
- **막혔던 점**
  - `for`를 써야 할 자리에 `if (int i = 0; ...)`라고 써서 컴파일 에러. `if` 괄호 안에는 조건식 하나만 올 수 있다.
  - `replace("[^a-zA-Z]", "")`가 아무것도 안 지웠다. **`replace`는 정규식이 아니라 문자 그대로를 찾는다.**
    - 두 메서드 모두 일치하는 부분을 **전부** 바꾼다. 차이는 첫 인자를 정규식으로 보느냐 문자 그대로 보느냐.
    - 정규식을 받는 String 메서드: `replaceAll`, `replaceFirst`, `matches`, `split` (파라미터 이름이 `regex`)
    - `split(".")`, `split("|")` 함정. 정규식 기호라서 `split("\\.")`처럼 이스케이프해야 한다.
  - 처음엔 알파벳만 남겼는데 문제 조건은 **영숫자(alphanumeric)**. `"0P"` 같은 입력에서 틀린다.
  - 인덱스를 `len - i`로 써서 범위를 벗어남. 마지막 인덱스는 `len - 1`이므로 `len - i - 1`.
- **더 알게 된 것: StringBuilder는 스레드 안전하지 않다**
  - 여러 스레드가 같은 `StringBuilder`에 동시에 `append()`하면 글자가 덮어써지거나 예외가 날 수 있음 (경쟁 상태).
  - 스레드 안전한 버전은 `StringBuffer` (메서드에 `synchronized`). 대신 동기화 비용 때문에 약간 느림.
  - 코딩테스트나 지역 변수처럼 스레드 하나만 쓰는 경우엔 `StringBuilder`가 맞다.

### P2. 문자열 뒤집기

- **난이도** ★ | [문제 링크](https://leetcode.com/problems/reverse-string/) | 책 풀이: [P2_1.java](../../src/ch06/P2_1.java) · [P2_2.kt](../../src/ch06/P2_2.kt) | 내 풀이: [P2.java](solutions/P2.java)
- **첫 시도** ✅ 자력 해결 / ⬜ 힌트 후 해결 / ⬜ 책 참고
- **접근**
  - 투 포인터 + swap. `start = 0`, `end = s.length - 1`에서 시작해 양 끝을 임시 변수 `tmp`로 맞바꾸고 안쪽으로 한 칸씩 좁힌다.
  - `start < end` 조건이라 길이가 홀수면 가운데 문자는 안 건드리고, 길이 1이면 반복문이 안 돈다.
- **복잡도** 시간 `O(n)` (교환 n/2번) / 공간 `O(1)` (`start`, `end`, `tmp` 변수 3개)
- **내 풀이 vs 책 풀이**
  - 책 풀이 P2_1과 사실상 같은 코드. P1 책 풀이에서 본 투 포인터를 바로 써먹었다.
  - Kotlin 풀이 P2_2는 `s[start] = s[end].also { s[end] = s[start] }`로 임시 변수 없이 한 줄 swap.
    1. `s[end]` 값을 먼저 꺼내 둔다.
    2. `also` 블록에서 `s[end]`에 `s[start]`를 넣는다.
    3. 꺼내 둔 원래 `s[end]` 값이 `s[start]`에 대입된다.
    - 자바엔 이런 문법이 없어서 임시 변수가 표준.
- **막혔던 점**
  - 없음. 대신 문제 조건 문장을 정리했다.
- **더 알게 된 것: in-place, O(1) extra memory**
  - `You must do this by modifying the input array in-place with O(1) extra memory.`
  - **in-place**: 새 배열에 결과를 만들지 말고, 받은 배열 `s` 자체를 고친다.
  - **O(1) extra memory**: n이 커져도 추가로 쓰는 메모리 양이 일정해야 한다. 입력 배열 자체는 "extra"에 포함 안 됨.

    | 코드 | 추가 메모리 |
    | --- | :---: |
    | `start`, `end`, `tmp` 변수만 사용 | O(1) |
    | `new char[n]`에 뒤집어 담기 | O(n) |
    | `new StringBuilder(...).reverse()` | O(n) |

  - **반환값이 `void`인데 답이 전달되는 이유**: 배열은 참조형이라 메서드는 배열 객체의 주소를 받는다. 그 주소로 찾아가 내용을 바꾸면 호출한 쪽의 원본 배열이 바뀐다. LeetCode는 함수가 끝난 뒤 원본 배열을 확인해서 채점한다.
    - 4장 원시형 vs 참조형과 이어지는 내용. 책 예제 [CallByValueExample.java](../../src/ch06/CallByValueExample.java)가 같은 동작(넘겨받은 리스트에 `add`하면 원본이 바뀜)을 보여준다.

### P3. 로그 파일 재정렬

- **난이도** ★ | [문제 링크](https://leetcode.com/problems/reorder-data-in-log-files/) | 책 풀이: [P3_1.java](../../src/ch06/P3_1.java) · [P3_2.kt](../../src/ch06/P3_2.kt) | 내 풀이: [P3.java](solutions/P3.java) · 첫 시도: [P3_v1.java](solutions/P3_v1.java)
- **첫 시도** ⬜ 자력 해결 / ✅ 힌트 후 해결 / ⬜ 책 참고
- **접근**
  - `Arrays.sort(logs, Comparator)` 하나로 조건 4개를 모두 처리. 종류는 **마지막 글자**가 숫자인지로 판별 (식별자 뒤 단어가 전부 숫자이거나 전부 소문자라서 가능).

    | 경우 | 반환값 | 조건 |
    | --- | --- | --- |
    | 둘 다 숫자 | `0` → 안정 정렬이 입력 순서 유지 | 숫자 로그 순서 유지 |
    | `a`만 숫자 | `1` (`b`가 앞) | 문자 로그가 앞 |
    | `b`만 숫자 | `-1` (`a`가 앞) | 문자 로그가 앞 |
    | 둘 다 문자 | `split(" ", 2)`로 식별자/내용 분리 → 내용 `compareTo` → 같으면 식별자 `compareTo` | 사전순, 같으면 식별자순 |

- **복잡도** 시간 `O(n log n)` (비교 1번에 로그 길이만큼 걸리지만 길이 ≤ 100) / 공간 `O(n)` (`Arrays.sort`의 객체 정렬(TimSort)이 내부에서 임시 배열을 씀)
- **내 풀이 vs 책 풀이**

  | | 내 풀이 | 책 풀이 (P3_1) |
  | --- | --- | --- |
  | 구조 | 비교 함수 하나가 4가지 경우 처리 | 문자 리스트 / 숫자 리스트로 먼저 나누고 문자 로그만 정렬 |
  | 문자 로그가 앞 | 비교 함수에서 `1` / `-1` | 문자 리스트 뒤에 숫자 리스트 `addAll` |
  | 숫자 로그 순서 유지 | `0` 반환 + 안정 정렬에 의존 | 숫자 로그는 아예 정렬 안 함 |
  | 문자 로그끼리 비교 | `split(" ", 2)` + `compareTo` | 같음 |
  | 종류 판별 | 마지막 글자 | `split(" ")[1].charAt(0)` |

  - 내 풀이는 안정 정렬 성질을 알고 활용해서 짧다. 책 풀이는 안정 정렬을 몰라도 맞고, 숫자 로그끼리는 비교하지 않아서 의도가 더 명시적이다.
  - 개선점: `arrA[1].compareTo(arrB[1])`를 두 번 호출함. 책처럼 `int compared`에 저장하면 한 번이면 된다.
  - **책 주석 오류**: "순서가 앞인 경우 1, 순서가 뒤인 경우 -1"은 반대. `s1`이 앞이면 음수, 뒤면 양수. 또 `compareTo`는 `±1`만이 아니라 `"a".compareTo("d") == -3`처럼 아무 정수나 반환한다. 부호만 의미 있어서 코드는 정상 동작.
  - `list.toArray(new String[0])`: List → 배열 변환 관용구. `new String[0]`은 타입을 알려주는 용도이고 크기는 자바가 알아서 맞춘다.
- **막혔던 점**
  - 처음엔 결과 배열에 하나씩 넣으면서 자리를 찾는 **삽입 정렬을 직접 구현**했다. 고칠 곳이 계속 생겼다.
    - 첫 시도 (파일 없음): 삽입 후 `break`가 가장 안쪽 `for (j ...)`만 빠져나와서, 바깥 `for (i ...)`가 같은 로그를 또 넣다가 `ArrayIndexOutOfBoundsException`. **중첩 반복문의 `break`는 자기를 감싼 반복문 하나만 빠져나온다.**
    - 두 번째 시도 ([P3_v1.java](solutions/P3_v1.java)): 비교 결과를 `isBig`에 먼저 담고 `switch`로 옮기도록 나눴지만,
      - 기존 문자 로그들보다 사전순으로 가장 뒤인데 숫자 로그가 없으면 넣을 곳이 없어서 로그가 사라짐
      - 밀기 반복문 조건이 반대(`while (m < i)`)라 한 번도 안 돌고 덮어씀
      - `switch` 안의 `break`는 `switch`만 빠져나옴 (`continue`는 바깥 반복문으로 감)
      - 숫자 로그를 맨 뒤와 swap해서 상대 순서가 바뀜
      - `replace(식별자 + " ", "")`는 일치하는 곳을 **전부** 지움 → `"a a b"`에서 내용의 `a`까지 지워짐
  - 깨달은 것: **비교는 비교만 해야 한다.** 비교와 자리 옮기기가 섞이면 제어 흐름이 꼬인다. → 비교 규칙만 짜고 정렬은 `Arrays.sort`에 맡기기.
- **더 알게 된 것: Comparator**
  - `Arrays.sort(배열, (a, b) -> { ... })`: 정렬 알고리즘은 자바가, "누가 앞인가" 규칙은 내가.
  - 반환값은 **부호만** 의미 있음: 음수 → `a`가 앞 / `0` → 같음 / 양수 → `b`가 앞.
  - 비교 약속: ① `compare(a, b)`와 `compare(b, a)`는 부호가 반대 ② a < b, b < c면 a < c ③ 0끼리도 일관. 어기면 `IllegalArgumentException: Comparison method violates its general contract!`
  - **`(a, b)`에 들어오는 순서는 원래 배열 순서와 무관.** `{"d","b","a","c"}` 정렬 시 첫 호출이 `compare(b, d)`였다. 그래서 비교 함수는 내용만 보고 판단해야 하고, "원래 순서 유지"는 `0` 반환 + 안정 정렬로 처리한다.
  - **안정 정렬**: 비교 결과가 0인 원소끼리 원래 순서 유지. 객체 배열용 `Arrays.sort`와 `List.sort`는 안정 정렬 보장 (원시형 배열용 `Arrays.sort`는 아님).
  - 숫자 비교는 `a - b` 대신 `Integer.compare(a, b)` (오버플로 방지), 문자열은 `a.compareTo(b)`.
  - boolean 부정은 `!`. `~`는 정수 비트 반전이라 boolean에 쓰면 컴파일 에러.

### P4. 가장 흔한 단어

- **난이도** ★ | [문제 링크](https://leetcode.com/problems/most-common-word/) | 책 풀이: [P4_1.java](../../src/ch06/P4_1.java) · [P4_2.kt](../../src/ch06/P4_2.kt) | 내 풀이: [P4.java](solutions/P4.java)
- **첫 시도** ⬜ 자력 해결 / ✅ 힌트 후 해결 / ⬜ 책 참고
- **접근**
  - 전처리: `replaceAll("[^a-zA-Z0-9]", " ")`로 구두점을 공백으로 바꾸고 `split(" +")`로 단어 분리, 단어마다 `toLowerCase()`.
  - `HashMap<String, Integer>`에 `getOrDefault(w, 0) + 1`로 개수 세기.
  - 키 목록을 개수 내림차순으로 정렬(`-compareTo`)한 뒤, 앞에서부터 금지 단어가 아닌 첫 단어를 반환.
- **복잡도** 시간 `O(n + k log k)` (n = 문단 길이, k = 서로 다른 단어 수, 정렬 때문에 k log k) / 공간 `O(n)`
- **내 풀이 vs 책 풀이**

  | | 내 풀이 | 책 풀이 (P4_1) |
  | --- | --- | --- |
  | 구두점 제거 | `[^a-zA-Z0-9]` → 공백, `split(" +")` | `\\W+` → 공백, `split(" ")` |
  | 소문자 변환 | 단어마다 | 문자열 전체에 한 번 |
  | 개수 세기 | `HashMap` + `getOrDefault` | 같음 |
  | 금지 단어 처리 | 정렬 후 하나씩 확인하며 건너뜀 | 셀 때부터 제외 |
  | 금지 단어 확인 | `Arrays.asList(banned).contains()` O(b) | `HashSet.contains()` O(1) |
  | 최댓값 찾기 | 전체 정렬 O(k log k) | `Collections.max` O(k) |

  - **1등 하나만 필요하면 정렬하지 말고 최댓값만 찾기.** `Collections.max(counts.entrySet(), Map.Entry.comparingByValue()).getKey()`
    - `Map.Entry.comparingByValue()`: 값 기준으로 비교하는 Comparator를 자바가 미리 만들어 둔 것. P3에서 직접 짠 `(a, b) -> ...`와 같은 역할.
  - 금지 단어를 처음부터 맵에 안 넣으면, 최댓값 찾을 때 따로 확인할 필요가 없다.
  - **"포함되어 있나?"를 자주 확인하면 `Set`.** 배열/리스트 `contains`는 앞에서부터 하나씩 비교하지만 `HashSet`은 해시로 바로 찾는다.
  - `\\w` = 단어 문자 `[a-zA-Z0-9_]`, 대문자 `\\W` = 그 반대. `\\W+`로 바꾸면 구두점·공백 덩어리가 공백 하나가 돼서 중간 빈 문자열이 안 생긴다. (내 풀이는 바꿀 때가 아니라 나눌 때 `" +"`로 처리)
  - **둘 다 가진 허점**: `trim()`이 없어서 문단이 구두점·공백으로 시작하면 맨 앞에 `""`가 생긴다. Kotlin 풀이(P4_2)는 `.trim().split("\\s+")`로 처리함.
- **막혔던 점**
  - `replaceAll("!|?|'|,|;|.", "")` → `PatternSyntaxException: Dangling meta character '?'`.
    - `?`는 정규식에서 "앞의 것이 0번 또는 1번"이라는 메타 문자. 앞이 `|`라 적용할 대상이 없어서 에러.
    - `.`도 메타 문자("아무 문자 하나")라서 그대로 두면 모든 글자가 지워진다.
    - 기호를 글자 그대로 쓰려면 **이스케이프**(`\\?`, `\\.`) 하거나 **대괄호** `[...]` 안에 넣는다.
  - `ball`과 `BALL`이 따로 세어짐 → 모든 단어가 1번씩 동점 → 엉뚱하게 `"the"` 반환.
    - 동점이면 정렬이 원래 순서를 유지하는데, **`HashMap`의 `keySet()` 순서는 넣은 순서가 아니다** (해시값에 따라 정해짐). 그래서 문장 순서도 사전순도 아닌 단어가 나왔다.
    - 대소문자 통일은 **세기 전에** 해야 한다.
  - 구두점을 공백으로 바꾸니 `"Bob. hIt"` → `"Bob  hIt"`(공백 2개) → `split(" ")`이 `["Bob", "", "hIt"]` → `""`가 가장 많이 세어짐.
    - `split(" ")`은 공백 하나하나가 구분자. 공백 덩어리를 하나로 보려면 `split(" +")` 또는 `split("\\s+")` (`+` = 앞의 것이 1번 이상).
    - `split`은 **맨 뒤** 빈 문자열은 버리지만 **중간·맨 앞**은 남긴다. 맨 앞은 `trim()`으로 해결.
    - 순서: 구두점 → 공백 / 소문자 / `trim()` / `split(" +")`
- **더 알게 된 것: `missing return statement`**
  - 반복문 안에서 `return`하는 건 괜찮지만, 반복문이 `return` 없이 끝나는 경로가 있으면 컴파일 에러.
  - 문제에서 "금지되지 않은 단어가 반드시 있다"고 보장해도 **컴파일러는 문제 조건을 모르고 코드 모양만 본다.**
  - 그래서 반복문 뒤에 실행될 일 없는 `return null;`(또는 `""`)을 둔다. 실무에서는 `throw new IllegalStateException()`으로 "여기 오면 잘못된 것"을 드러내기도 한다.
  - `if`/`else` 양쪽에 다 `return`이 있으면 괜찮다. 반복문은 몇 번 돌지 몰라서 컴파일러가 판단할 수 없다.

### P5. 그룹 애너그램

- **난이도** ★★ | [문제 링크](https://leetcode.com/problems/group-anagrams/) | 책 풀이: [P5_1.java](../../src/ch06/P5_1.java) · [P5_2.kt](../../src/ch06/P5_2.kt) | 내 풀이: [P5.java](solutions/P5.java)
- **첫 시도** ⬜ 자력 해결 / ✅ 힌트 후 해결 / ⬜ 책 참고
- **접근**
  - **애너그램끼리는 글자를 정렬하면 같은 문자열이 된다.** `"eat"`, `"tea"`, `"ate"` → 모두 `"aet"`
  - 정렬한 문자열을 키로 `HashMap<String, List<String>>`에 모은다: `toCharArray()` → `Arrays.sort()` → `new String(chars)`
  - 키가 있으면 그 리스트에 `add`, 없으면 새 리스트를 만들어 `put`. 마지막에 맵의 값들을 결과 리스트로.
- **복잡도** 시간 `O(n · k log k)` (n = 단어 수, k = 단어 최대 길이, 단어마다 글자 정렬) / 공간 `O(n · k)` (모든 단어가 맵에 들어감)
- **내 풀이 vs 책 풀이**

  | | 내 풀이 | 책 풀이 (P5_1) |
  | --- | --- | --- |
  | 키 만들기 | `new String(chars)` | `String.valueOf(chars)` (결과 같음) |
  | 키가 없을 때 | 리스트 만들고 단어 넣고 `put` | 빈 리스트만 `put`하고 아래에서 공통으로 `add` |
  | 결과 만들기 | `keySet()` 돌면서 그룹마다 `new ArrayList<>(...)`로 복사 | `new ArrayList<>(map.values())` 한 줄 |

  - 구조는 거의 같다. 차이는 마무리 부분.
  - **`map.values()`**: 값들만 모아준다. 키를 하나씩 꺼내 `get`할 필요 없음. 그룹마다 복사본을 만든 것도 불필요한 작업이었다.
  - **`computeIfAbsent`**로 `if/else`를 한 줄로: `map.computeIfAbsent(key, k -> new ArrayList<>()).add(str);`
    - 키가 없으면 새 리스트를 만들어 넣고, 있든 없든 그 키의 리스트를 반환 → 바로 `.add()`를 붙일 수 있다.
    - Kotlin 풀이(P5_2)의 `getOrPut`이 같은 역할.
    - P4의 `getOrDefault`와 다른 점: `getOrDefault`는 기본값을 **돌려주기만** 하고 맵에 넣지 않는다.
  - 더 빠른 키: 글자 정렬 대신 알파벳 26개의 개수를 세서 키로 쓰면(`"eat"` → `a1e1t1`) 정렬이 없어서 `O(n · k)`.
- **막혔던 점**
  - 첫 시도는 맵 없이 `List<List<String>>`를 돌면서 각 그룹 첫 단어를 정렬해 비교했다. 문제가 3개 있었다.
    - `answer`가 빈 리스트로 시작해서 `for (List<String> list : answer)`가 한 번도 안 돎 → 빈 결과. `list.isEmpty()`는 `answer`가 아니라 **그룹 하나**가 비었는지 확인하는 코드였다.
    - for-each로 도는 중에 `answer.add()` → `ConcurrentModificationException`. **순회 중인 컬렉션에 추가·삭제하면 안 된다.**
    - 첫 그룹과 다르면 바로 `else`에서 새 그룹을 만들었다. "어느 그룹에도 없다"는 **전부 확인한 뒤에야** 알 수 있다 → `found` 플래그 + `break`, 반복문 밖에서 새 그룹. (P3 첫 시도의 "비교와 자리 옮기기를 섞지 말자"와 같은 패턴)
  - 고쳐도 단어마다 모든 그룹을 돌며 첫 단어를 매번 다시 정렬해서 느리다. → "정렬한 문자열로 그룹을 **바로** 찾을 수 없을까?" 힌트를 듣고 P4에서 쓴 `HashMap`을 떠올림.
  - 깨달은 것: **"같은 기준끼리 묶기" = 그 기준을 키로 하는 `Map<기준, List>`.**
