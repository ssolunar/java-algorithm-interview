### 원시 자료형 vs 참조 자료형 (메모리·속도 차이)

- 원시 자료형 : 기본 자료형이다. 자바에는 8개 있음. byte, short, int, long, float, double, boolean, char 각 자료형 별로 크기가 정해져있음.
- 참조 자료형 : 원시형이 아닌 모든 자료형, 메모리에 직접 값을 채워넣는 원시형과 다르게 참조 자료형은 모두 크기가 동일하고 해당 메모리에는 실제 값의 주소값을 적는게 특징이다.
- 속도 : 원시형은 메모리에 값이 직접 저장되어 있어서 가져다 쓰면되는데 참조형은 주소값이 적혀있어 실제 값을 확인하기 위해서는 주소로 이동해야함. 그래서 속도가 더 느림
- 그외 차이점
    - 원시형은 자바 메모리 모델에서 훨씬 더 빠른 영역에 할당된다.
    - 원시형은 자료형에 따라 크기가 제각각. 참조형 모두 동일
    - 참조형은 메서드 호출을 통해 여러 편리한 작업 수행
    - 원시형은 값이 항상 존재해야함. 참조형은 null 허용
    - 컬렉션의 엘리먼트는 참조형만 가능
    - 원시형은 소문자로 시작, 참조형은 대문자로 시작

### 오토박싱이 성능에 미치는 영향

- 오토박싱이란? : 자바에서 원시형과 참조형을 자동으로 변환해주는 기능. 컴파일러가 변환 코드를 자동으로 끼워 넣는 것이라 내 코드엔 안 보이지만 바이트코드엔 있다.
- 래퍼 클래스 (Wrapper Class) : 원시형에 대응하는 참조형
- 참조형은 클래스 객체임으로 다양한 메서드를 제공

```java
Integer boxed = 10;      // 실제로는 Integer.valueOf(10)  <- 박싱
int unboxed = boxed;     // 실제로는 boxed.intValue()     <- 언박싱
```

편의 문법일 뿐 공짜가 아니다. 특히 `sum += i` 한 줄이 반복문 안에 있으면
**매 반복마다 언박싱 -> 덧셈 -> 박싱**이 일어난다.

#### 왜 느린가 (3가지)

1. **객체 할당 비용** — `int`는 4바이트 값 자체지만 `Integer`는 힙에 객체를 만들고
   (객체 헤더 12~16바이트 + 값 4바이트) 그 주소를 들고 있다. 값 하나당 메모리 4배 + 할당 작업.
2. **GC 압박** — 박싱은 캐시 범위 밖이면 매번 *새 객체*를 만든다. 1억 번 루프면 1억 개의
   쓰레기 객체가 생기고 GC가 계속 치운다. 체감 속도 차이의 대부분이 여기서 온다.
3. **캐시 지역성 / 역참조** — `int[]`는 값이 메모리에 연속으로 붙어 있어 CPU 캐시에 통째로
   올라온다. `Integer[]`는 주소만 연속이고 실제 값은 힙에 흩어져 있어 순회할 때마다
   주소를 따라 점프해야 한다 (cache miss).

> 책 예제 대응: `JavaPerf`(4장) = 1번·3번 / `AutoBoxingPerf`(9장) = 1번·2번

#### Integer 캐시 — 면접 단골 함정

`Integer.valueOf()`는 **-128 ~ 127** 범위의 값에 대해 미리 만들어 둔 객체를 **재사용**한다.

```java
Integer a = 127, b = 127;
a == b;          // true   <- 같은 캐시 객체
Integer c = 128, d = 128;
c == d;          // false  <- 각각 새 객체
c.equals(d);     // true
```

`c == d`가 false인 건 128이라는 값에 문제가 있어서가 아니라 **객체가 두 개라 주소가 달라서**다.
값은 둘 다 128로 같다. 127까지 true가 나오는 쪽이 오히려 예외 상황(캐시 재사용).

`==`가 비교하는 대상이 타입에 따라 다른 게 원인:

| 타입 | `==`가 비교하는 것 |
| --- | --- |
| `int` (원시형) | **값 자체** — 메모리에 값이 직접 있으니 값을 맞대봄 |
| `Integer` (참조형) | **주소** — 메모리에 주소가 있으니 주소를 맞대봄 |

```java
int a = 128, b = 128;
a == b;                        // true  OK — 원시형은 값이 뭐든 항상 안전
Integer c = 128, d = 128;
c == d;                        // false 주소 비교
c.equals(d);                   // true  값 비교
c.intValue() == d.intValue();  // true  언박싱 후 값 비교
```

> **규칙**: 변수 타입이 대문자로 시작하면(`Integer`, `Long`, `String`...) `==` 대신 `.equals()`.
> 소문자면(`int`, `long`, `char`...) `==` 그대로.

여기서 파생되는 포인트 — `JavaPerf`의 `Integer[]`에 넣는 값이 `1`이라 **전부 캐시 히트**다.
즉 그 예제의 삽입 시간 차이는 객체 생성 비용이 아니라 순수하게 참조 저장 + 역참조 비용.
값을 `100000`으로 바꿔 돌리면 훨씬 더 느려진다.

#### null 언박싱 -> NPE

```java
Map<String, Integer> map = new HashMap<>();
int count = map.get("없는키");   // NPE! null.intValue()
```

`Integer`는 null을 담을 수 있는데 원시형에 대입하는 순간 `.intValue()`가 호출된다.
`getOrDefault()`를 쓰는 습관이 여기서 나온다.

#### 알고리즘 문제에서의 실전 규칙

| 상황 | 쓰는 것 | 이유 |
| --- | --- | --- |
| 루프 누적 변수 | `int` / `long` | `Integer sum`은 반복마다 객체 생성 |
| 큰 수열 저장 | `int[]` | `List<Integer>` 대비 메모리 4배·캐시 미스 |
| 값 세기 (범위 작음) | `int[26]`, `int[128]` | `Map<Character, Integer>`보다 압도적으로 빠름 |
| 값 세기 (범위 큼) | `HashMap` 불가피 | 대신 `merge` / `getOrDefault`로 박싱 횟수 줄이기 |
| 래퍼 값 비교 | `.equals()` | `==`는 128부터 깨짐 |

트레이드오프 — `Arrays.sort(int[])`는 듀얼 피벗 퀵소트라 빠르지만 내림차순 정렬이나
커스텀 `Comparator`를 못 쓴다. 그게 필요하면 `Integer[]`로 박싱해야 하고, 대신 팀소트라
**안정 정렬**이 된다. (17장에서 다시)

> 오토박싱은 문법적 편의일 뿐, 반복문 안에서는 **객체 생성 + GC + 캐시 미스** 3중 비용을 낸다.
> 성능이 중요한 구간에서는 원시형과 원시 배열을 쓴다.

### 컬렉션 프레임워크 계층 구조와 구현체별 특성

- 왜 컬렉션에는 참조형만 저장할 수 있을까? 컬렉션 클래스에는 단순히 값을 저장하는게 아니라 객체를 저장하는게 자바의 결정이었음 -> 메서드를 지원해야함 -> 이건 참조형 밖에 없어.

- 자바 컬렉션 프레임워크 : 컬렉션 자료구조를 구현한 공식 라이브러리
- 이점 : 일관성, 개발비용절약, 고성능 구현, 재사용성
- 구성 : Collection과 Map이 최상위 인터페이스이고, Collection을 상속받은 List, Set, Queue, Deque 인터페이스가 있다.
- 인터페이스 와 구현 클래스 : 인터페이스는 명세서, 구현 클래스 는 실제 기능 구현코드 들어있음

#### List
- ArrayList
- LinkedList
- Vector : 성능문제로 안씀

#### Map
- HashMap
- LinkedHashMap
- TreeMap
- HashTable : 성능문제로 안씀
